\begin{abstract}
\noindent
This specification defines \Hr{}, an installer for macOS that leaves a person, a
few minutes after double-clicking one file, with a working \Nd{} shard on their own
machine: two validators by default, a read-only observer joined to them, and the
\Gz{} browser configured to deploy to the shard and read from it, paying from a
wallet that the shard's genesis has funded. A configuration panel lets the user
change the number of validators, from two up to ten, either by growing or shrinking
the running shard (new validators join, are funded and bond at the next epoch;
departing ones withdraw first) or by starting a new shard of the chosen size. The
specification fixes the artifact (a signed, notarised product archive carrying
\Gz{} and the \Hr{} menu-bar application, which owns the shard), first-run
provisioning, the supervision of every node by one per-user launch agent, the
configuration written to each program, the resizing procedure, the security model,
upgrade, reset and uninstall, the build and release pipeline, and acceptance tests.
It is grounded in a review of \Nd{} at \code{fce422a}, \Gz{} at \code{f6ee26a} and
\Camp{} at \code{b46e16c} (with \Gz{}'s pinned \Camp{} revision \code{ea2d323}),
and of the \Gz{} architecture proposal and implementation specification in
\code{publications/f1r3gaze}.

Version 0.3 replaces the single standalone validator of version 0.2 with the
multi-validator topology the node repository already runs and tests
(\code{docker/shard.yml}), generalised to $N$ validators on loopback.
\end{abstract}

\section{Scope and conventions}\label{sec:scope}

\subsection{What the installer delivers}

After a successful install on a supported Mac, with no further action beyond
approving a background item in System Settings when macOS asks:

\begin{enumerate}[nosep]
\item \code{/Applications/F1R3Gaze.app} and \code{/Applications/ign1t10n.app} are
  installed, signed and notarised.
\item A per-user launch agent, \code{io.f1r3fly.ign1t10n.supervisor}, is registered
  and running. It supervises the shard's nodes:
  \begin{itemize}[nosep]
  \item a \emph{bootstrap} node, which coordinated the genesis ceremony and is every
    other node's rendezvous; it is not bonded and never proposes;
  \item $N$ \emph{validators}, bonded at genesis, which propose and finalise blocks
    ($N = 2$ unless the user has chosen otherwise, $2 \le N \le 10$);
  \item one \emph{observer}, a read-only node that serves every read the browser
    makes.
  \end{itemize}
\item Every key was generated on this machine at install time. The shard's genesis
  funds the user's active \Gz{} wallet and a local faucet.
\item \Gz{} deploys to validator~1, reads from the observer, and is open in a window.
\item Every listening socket of every node is bound to the loopback interface.
\item The shard survives logout, sleep and reboot, and comes back with its chain
  intact, at the size last chosen.
\end{enumerate}

\noindent
Throughout, ``$N$ nodes'' in the user interface means $N$ validators; the bootstrap
and the observer are always present and are shown separately. With the default,
five \code{f1r3node} processes run: bootstrap, two validators, observer.

\subsection{Non-goals for this version}

More than ten validators; joining a remote or public shard; exposing the local shard
to the network; stake other than equal stakes; Linux and Windows (the \Gz{} release
already ships those installers, but the shard bundle here is macOS-only); bundling
the Embers service; Docker.

\section{Findings from the code review}\label{sec:findings}

These are the facts the design rests on. Each cites where it was established.

\begin{finding}[The observer is not optional]\label{f:readonly}
Every endpoint that runs an exploratory deploy is served only by read-only nodes;
a validator answers \code{400 readonly\_node\_required}. The list
(\code{docs/node/api-reference.md}) includes \code{POST /api/explore-deploy},
\code{POST /api/estimate-cost}, \code{GET /api/registry/\{uri\}} and
\code{GET /api/balance/\{address\}}. \Gz{}'s shard bridge uses exactly these: it
resolves sites and reads registry values at observers
(\code{gaze-shard/src/bridge.rs}, \code{graded}), quotes the cost of a deploy by
\code{estimate\_cost} on the first observer, subscribes to \code{/ws/events} on the
first observer, and sends deploys to the validator.
\end{finding}

\begin{finding}[The shipped topologies]\label{f:topology}
The repository runs two topologies. \emph{Standalone} (\code{docker/standalone.yml}):
one bonded node that is its own ceremony master, with no peers. \emph{Shard}
(\code{docker/shard.yml}): a bootstrap node started with
\code{--ceremony-master-mode}, \code{--required-signatures}, and
\code{--heartbeat-disabled}, bootstrapping from itself and absent from
\code{bonds.txt} (``The bootstrap node is NOT a validator'',
\code{docker/conf/bootstrap.conf}); genesis validators started with
\code{--genesis-validator} and \code{--bootstrap} pointing at it; and an observer
bootstrapping from it. Nothing in the repository pairs a standalone node with an
observer, and that pairing proved awkward in practice; the shard topology is the one
that is tested (CI smoke, soak runs). This specification adopts the shard topology,
generalised from three validators to $N$.
\end{finding}

\begin{finding}[Same host, distinct ports]\label{f:loopback}
In \code{shard.yml} every node listens on the same six container ports and is told
apart by its Docker hostname; the host publishes them at 40400, 40410, 40420, 40430
(and 40440 for \code{validator4.yml}) and 40450 for the observer
(\code{docker/README.md}, ``Port Mapping''). On one Mac without Docker every node
must advertise \code{127.0.0.1} and differ by port. The node supports per-node ports
through configuration and \code{--host}; that a set of nodes on one loopback address
discover and gossip correctly is expected but untested (Obligation~\ref{ob:topology}).
\end{finding}

\begin{finding}[The browser's default validator would be the bootstrap]\label{f:defaults}
\code{ShardConfig::default()} in \Gz{} is validator \code{http://localhost:40403},
observers \code{[http://localhost:40453]}, shard id \code{root}, quorum 2. In the
shard topology port 40403 is the \emph{bootstrap}, which is not bonded. A node that
cannot propose accepts a deploy and strands it, because deploy queues are node-local
(\code{docs/node/joining-a-network.md}, and \code{/api/pending-deploys} in the API
reference). \Hr{} therefore always writes \Gz{}'s \code{validator} explicitly, to
validator~1. With one observer the bridge returns the \emph{node} rung and never
consults the quorum, so \Hr{} writes \code{quorum = 1}.
\end{finding}

\begin{finding}[The shard can be resized while running]\label{f:resize}
The join guide (\code{docs/node/joining-a-network.md}) specifies how a node that was
not at genesis joins (last-finalised-state fetch from \code{--bootstrap}) and becomes
a validator: start it already carrying its validator key; fund its vault by transfer
from a funded key; submit a bond deploy \emph{to a bonded validator}, signed by the
joiner's own key (\code{rholang/examples/bond/bond.rho}, calling
\code{PoS!("bond", deployerId, amount, ret)}); the bond takes effect at the next epoch
boundary, observable at \code{GET /api/bond-status/\{pk\}}. Leaving is the mirror
image: \code{PoS!("withdraw", deployerId, ret)} (\code{casper/src/main/resources/PoS.rhox},
line 370) takes the validator out of the active set at the next boundary and pays out
stake after the quarantine. The shard configuration sets \code{epoch-length = 10}
and \code{quarantine-length = 10} (\code{docker/conf/default.conf}), so both take
seconds to a few minutes locally, not the thousands of blocks of the node defaults.
The guide warns: ``Only bond a validator you intend to keep running. A bonded
validator that does not propose is counted in consensus while contributing nothing
to it.''
\end{finding}

\begin{finding}[Deploys can be signed outside the node]\label{f:signing}
\Gz{}'s \code{gaze-shard} produces deploys byte-for-byte as the node verifies them
(tested against \code{prost}), and \code{gaze-wallet} renders the vault transfer
template (\code{render\_transfer}) and derives F1R3Cap addresses. \Hr{} reuses both
crates, pinned to the \Gz{} release it ships, for faucet transfers, bond and withdraw
deploys, so it needs neither the node's \code{deploy} subcommand nor an external
client.
\end{finding}

\begin{finding}[The shipped development keys are public]\label{f:devkey}
\code{docker/.env.example} (and the committed \code{docker/.env}) carry the private
keys of the bootstrap, four validators and the standalone node; their public keys are
the entries of \code{docker/genesis/bonds.txt} and \code{standalone-bonds.txt}, and
the vaults they control hold the genesis supply. Any install reusing them would give
every reader of the repository the validator keys and the funds.
\end{finding}

\begin{finding}[How a key can reach the node]\label{f:keypath}
\code{--validator-private-key} puts the key in the process's argument vector, which
any local user can read with \code{ps}; \code{shard.yml} uses it, which is harmless in
a container but not on a shared Mac. \code{--validator-private-key-path} takes an
encrypted PEM, decrypted with OpenSSL (\code{Secp256k1::parse\_pem\_file}); the
password comes from \code{F1R3NODE\_VALIDATOR\_PASSWORD}, or else from an
interactive prompt (\code{node/src/rust/effects/console\_io.rs}).
\end{finding}

\begin{finding}[Everything listens on all interfaces]\label{f:bind}
\code{api-server.host} defaults to \code{0.0.0.0} and is configurable. The protocol
transport binds \code{0.0.0.0} unconditionally
(line 600 of \code{grpc\_transport\_receiver.rs} in \code{comm/src/rust/transport}). With up to
twelve nodes, that would be up to seventy-two sockets, including internal gRPC
(propose) and admin APIs, open to whatever network the laptop joins.
\end{finding}

\begin{finding}[Native linking on macOS]\label{f:linking}
The \code{crypto} crate depends on \code{openssl 0.10} without the \code{vendored}
feature, so a macOS build links Homebrew's \code{libssl}/\code{libcrypto}
dynamically. LMDB is compiled from source through \code{heed}; \code{aws-lc-sys},
\code{zstd-sys} and \code{bzip2-sys} link statically. \code{protoc} is build-time
only. No workflow in the repository builds for macOS.
\end{finding}

\begin{finding}[\Gz{} already packages itself for macOS]\label{f:gazepkg}
\code{packaging/macos/package.sh} builds a universal bundle,
\code{io.f1r3fly.f1r3gaze}, minimum macOS 11, signed with the hardened runtime and
\emph{empty} entitlements, in a signed, notarised, stapled DMG. Wallet keys live in
the Keychain under service \code{F1R3Gaze}. \code{settings.conf} is
\code{key = value} and the last assignment of a key wins
(\code{gaze-shell/src/profile.rs}); if the file is absent at first load \Gz{} writes a
commented template.
\end{finding}

\begin{finding}[The browser's wallet can be funded at genesis]\label{f:wallet}
\Gz{} wallet addresses are F1R3Cap addresses, the same base58 form as the vault
addresses in the node's \code{wallets.txt}. The active wallet signs, and pays for,
every deploy the browser makes. Balances and transfers go through Embers only; with
\code{embers\_api} unset the wallet panel reports that balances need Embers.
\end{finding}

\begin{finding}[Lifecycle facts]\label{f:lifecycle}
The node handles \code{SIGTERM} and \code{SIGINT}. A joined node restarted on the same
data directory reconnects in about a second; its identity is the TLS certificate in
the data directory, so a data directory must never be deleted while peers remember it.
The genesis ceremony in \code{default.conf} checks for signatures every 10\,s
(\code{approve-interval}) and waits at most a minute (\code{approve-duration}).
\end{finding}

\subsection{Principles}

\begin{principle}[Per-user, unprivileged at run time]
Administrator rights are used once, by Installer.app, to copy two bundles into
\code{/Applications}. Everything after that runs as the logged-in user.
\end{principle}

\begin{principle}[Loopback only]
No socket of any node listens on a non-loopback address.
\end{principle}

\begin{principle}[Fresh secrets]
Every key and password is generated on the user's machine. None is shipped.
\end{principle}

\begin{principle}[One owner for the shard]
A single supervisor starts, orders, monitors, resizes and stops every node. launchd
keeps the supervisor alive; the supervisor keeps the nodes alive. Per-node launch
agents were rejected: launchd has no dependency ordering, and resizing must be one
transaction over several nodes.
\end{principle}

\begin{principle}[A bonded validator runs]
A validator in the active set is never stopped on its own. Removing a validator means
withdrawing it first and stopping it only after it has left the active set
(Finding~\ref{f:resize}). The shard as a whole may be stopped; all validators then
stop together.
\end{principle}

\begin{principle}[Touch only what was created]
\Hr{} never deletes or overwrites data it did not create: never a \Gz{} wallet, never
\Gz{} settings outside its own managed block, never \code{\textasciitilde/.rnode}.
\end{principle}

\begin{principle}[Idempotent, resumable operations]
Provisioning and every resize are sequences of steps whose completion is recorded in
\code{shard.toml}. Interrupted at any point, each resumes at its first incomplete
step.
\end{principle}

\section{The distribution artifact}\label{sec:artifact}

\begin{requirement}[Product archive]
The release artifact \MUST{} be a flat product archive,
\code{ign1t10n-}$v$\code{-macos-universal.pkg}, built with \code{productbuild} from
two component packages (\code{io.f1r3fly.f1r3gaze.pkg},
\code{io.f1r3fly.ign1t10n.pkg}), signed with a \emph{Developer ID Installer}
certificate, notarised, and stapled. Each component \MUST{} install its bundle to
\code{/Applications} with bundle-version checking on, so an installed newer \Gz{} is
not downgraded.
\end{requirement}

A DMG was rejected because drag-and-drop cannot launch anything, and the brief asks
that the install end with the shard and the browser running.

\begin{requirement}[The post-install hook does one thing]
The \code{postinstall} script of the component package \code{io.f1r3fly.ign1t10n.pkg}
\MUST{} do nothing but launch \Hr{} in the console user's session:
\begin{lstlisting}[language=bash]
#!/bin/bash
user=$(stat -f %Su /dev/console)
[ "$user" = root ] || [ -z "$user" ] && exit 0      # no GUI session: first launch will do it
uid=$(id -u "$user")
launchctl asuser "$uid" sudo -u "$user" \
  open -g -a /Applications/ign1t10n.app --args --first-run
exit 0
\end{lstlisting}
It \MUSTNOT{} create files in the user's home, register agents or generate keys. It
\MUST{} exit 0 even if the launch fails, so a headless install succeeds and
provisioning happens at first launch.
\end{requirement}

\begin{requirement}[Platforms]
The artifact \MUST{} run on Apple silicon and \SHOULD{} run on Intel
(Decision~\ref{dec:arch}); every Mach-O is universal. The minimum macOS is 13.0, the
first release with \code{SMAppService} (Decision~\ref{dec:macos}).
\end{requirement}

\begin{requirement}[No dynamic dependencies outside the system]
For every Mach-O in the archive, \code{otool -L} \MUST{} list only paths under
\code{/usr/lib} and \code{/System/Library}.
\end{requirement}

\subsection{One binary, three roles}

\code{ign1t10n} is written in Rust (stable 1.91, matching \Gz{}), using \code{objc2}
bindings for AppKit, ServiceManagement and Security; \code{k256} and \code{pkcs8} for
keys; \code{gaze-shard} and \code{gaze-wallet} for deploys, transfers and addresses
(Finding~\ref{f:signing}); \code{toml} and \code{serde} for the manifest; a blocking
HTTP client for the node APIs.

\begin{description}[leftmargin=1.5em,style=nextline]
\item[\code{ign1t10n} (no arguments)] The menu-bar application and the configuration
  panel. On first run it opens the first-run window and drives provisioning. It never
  runs a node itself; it talks to the supervisor over the control socket.
\item[\code{ign1t10n supervise}] The launch agent's program. Owns every node process
  and executes resizes (\S\ref{sec:supervise}, \S\ref{sec:resize}).
\item[\code{ign1t10n ctl} \textit{verb}] A command-line client of the control
  socket: \code{status [--json]}, \code{start}, \code{stop}, \code{restart},
  \code{resize} \textit{N} \code{[--new-shard]}, \code{fund} \textit{address amount},
  \code{logs} \textit{node}, \code{env}, \code{reset}, \code{uninstall}. It is what the
  tests drive.
\end{description}

The control socket is \code{run/control.sock} in the state directory, a Unix-domain
socket in a \code{0700} directory carrying one JSON object per line. The supervisor
\MUST{} check the peer's user id (\code{getpeereid}) and refuse any other user.

\subsection{Keys and Keychain items}

Every key is a secp256k1 key written as an \code{ENCRYPTED PRIVATE KEY} PEM (PKCS\#8,
PBES2, PBKDF2-HMAC-SHA256 with 600\,000 iterations, AES-256-CBC), which OpenSSL
decrypts and \code{parse\_pem\_file} accepts. Each PEM has its own random 32-byte
password in a Keychain item of service \code{io.f1r3fly.ign1t10n}, account
\code{pem.}\textit{name} (\code{pem.bootstrap}, \code{pem.validator-3},
\code{pem.faucet}, \ldots). The items' access control list is the application's
designated requirement, so the menu bar, supervisor and \code{ctl} (one binary) read
them without a prompt and other programs cannot. A node receives its password only in
its own environment; the faucet key is decrypted only inside \Hr{} when it signs.

\section{Provisioning}\label{sec:prov}

Provisioning runs in the menu-bar process, as the user, when \code{shard.toml} is
absent or records an incomplete stage. It creates a shard of $N_0$ validators, $N_0$
being 2 unless the first-run window's ``Advanced'' disclosure was used to choose
another value in $[2, 10]$.

\subsection{S0: preflight}
Checks: macOS $\ge$ 13; \code{F1R3Gaze.app} present with bundle identifier
\code{io.f1r3fly.f1r3gaze} and a valid signature from the same team as \Hr{}; free
disk of at least $D_{\min}(N_0)$ and physical memory of at least $M_{\min}(N_0)$
(\S\ref{sec:budget}); the state directory creatable.

\subsection{S1: ports}\label{sec:ports}
Each node needs six ports (protocol, gRPC external, gRPC internal, HTTP, discovery,
admin) at offsets $+0\ldots{+5}$ from a base. The port plan follows the node's own
convention (Finding~\ref{f:loopback}) and keeps the observer where \Gz{} expects it:

\begin{center}\small
\renewcommand{\arraystretch}{1.1}
\begin{tabular}{@{}lccl@{}}
\toprule
Node & base & HTTP & note\\
\midrule
bootstrap & 40400 & 40403 & \\
validator 1--4 & 40410, 40420, 40430, 40440 & 40413, \ldots, 40443 & as \code{shard.yml}, \code{validator4.yml}\\
observer & 40450 & 40453 & \Gz{}'s default observer\\
validator 5--10 & 40460, 40470, \ldots, 40510 & 40463, \ldots, 40513 & skips the observer's decade\\
\bottomrule
\end{tabular}
\end{center}

\noindent
A base is usable if its six ports bind on \code{127.0.0.1}. Each node's base is
allocated independently: the plan's base if usable, otherwise the first usable base in
$41400, 41410, \ldots, 49990$. Allocated bases are recorded per node in
\code{shard.toml} and reused on every start; slots not yet in use are not reserved.

\subsection{S2: the paying wallet}
Using work package G1: \code{f1r3gaze wallet active --porcelain}; if there is no active
wallet, \code{f1r3gaze wallet new "Local shard" --porcelain}. The address is recorded
as \code{wallet.funded}. \Hr{} never sees the key.

\subsection{S3: keys}
Generate keys for the bootstrap (which signs as ceremony master but is not bonded), for
validators $1..N_0$, and for the faucet, each with its PEM and Keychain item. Record
every public key and F1R3Cap address. A unit test \MUST{} round-trip a PEM written
this way through \code{parse\_pem\_file} from the pinned \Nd{}.

\subsection{S4: genesis files}
\begin{lstlisting}[language=Conf]

04a1...9e 1000
04c7...31 1000
# genesis/wallets.txt: <F1R3Cap address>,<balance in dust>   (8 decimals)
<wallet.funded>,100000000000000        # 1 000 000 F1R3: the browser's wallet
<validator 1 address>,100000000000     # 1 000 F1R3 each: fees for its own withdraw
<validator 2 address>,100000000000
<faucet address>,49800000000000000     # the rest of the dev supply
\end{lstlisting}
The amounts are Decision~\ref{dec:amounts}; the faucet's balance leaves room for eight
further validators' stakes and fees.

\subsection{S5: node configurations}
Render \code{conf/common.conf} (network id \code{ign1t10n-}\textit{8 random hex
digits}, fresh at each genesis; shard name \code{root}; the consensus, genesis and
epoch parameters of \code{docker/conf/default.conf} with \code{required-signatures}
$= N_0$; logging; loopback binding) and one small file per node that includes it and
sets that node's ports, data directory and role (Appendix A).

\subsection{S6: register the agent}
\code{SMAppService.agent(plistName: "io.f1r3fly.ign1t10n.supervisor.plist").register()};
if the status is \code{requiresApproval}, the first-run window explains and offers
\code{SMAppService.openSystemSettingsLoginItems()}, then waits for \code{enabled}.

\subsection{S7: genesis}
The supervisor performs the genesis start:
\begin{enumerate}[nosep]
\item Start the bootstrap; wait for its \code{/api/status} to answer; record its node
  id from the \code{address} field.
\item Start validators $1..N_0$ with \code{--genesis-validator} and
  \code{--bootstrap} at the bootstrap.
\item Wait until every validator's and the bootstrap's \code{/api/ready} answers 200
  (the ceremony has gathered $N_0$ signatures and every node has the approved block).
  Record the genesis block hash.
\item Start the observer bootstrapping from the bootstrap; wait for its
  \code{/api/ready}.
\item Verify each genesis validator with \code{GET /api/bond-status/\{pk\}}.
\end{enumerate}

\subsection{S8: configure \Gz{}}\label{sec:gazeconf}
With work package G3, write \code{settings.d/50-ign1t10n.conf}; until G3 lands,
maintain a managed block at the end of \code{settings.conf}, which governs the keys it
sets because the last assignment wins (Finding~\ref{f:gazepkg}):
\begin{lstlisting}[language=Conf]
# >>> managed by ign1t10n: do not edit inside this block >>>
validator = http://127.0.0.1:40413
observers = http://127.0.0.1:40453
shard_id = root
quorum = 1
phlo_price = 1
# <<< managed by ign1t10n <<<
\end{lstlisting}
If the profile already names a non-loopback validator or observer, the first-run
window asks before pointing \Gz{} at the local shard; the choice is a toggle in the
configuration panel afterwards.

\subsection{S9: open the browser}
\code{open -b io.f1r3fly.f1r3gaze --args gaze://newtab}, only after the observer is
ready. The first-run window closes with a summary: shard id, validator count, the
funded wallet and its balance, and where the logs are.

\subsection{Budgets}\label{sec:budget}
Targets on an M-series Mac with $N_0 = 2$, measured by the acceptance suite: S0--S6
under 10\,s of machine time (approval excluded); S7 steps 1--3 (genesis) under
120\,s, given the 10\,s approve interval; observer join under 180\,s; whole first run
under five minutes.

$M_{\min}(N)$ and $D_{\min}(N)$ are $(N+2)$ times the per-node resident memory and
disk measured by Obligation~\ref{ob:footprint} at the pinned node version, plus a
margin; they are compiled into \Hr{} from that measurement, not guessed. The
configuration panel uses the same figures (\S\ref{sec:panel}).

\section{Supervision}\label{sec:supervise}

\subsection{Start}\label{sec:start}
\begin{enumerate}[nosep]
\item Read \code{shard.toml}; refuse to start if the installed \code{f1r3node} is
  incompatible with the recorded storage format (\S\ref{sec:upgrade}); resume any
  incomplete resize (\S\ref{sec:resize}) after the start.
\item Probe every recorded port on \code{127.0.0.1}; on conflict go to
  \S\ref{sec:portfail}.
\item Start the bootstrap; wait for \code{/api/ready} (120\,s).
\item Start every validator whose recorded state is \code{active},
  \code{joining}, \code{bonding} or \code{retiring}, in parallel; wait for each
  \code{/api/ready} (120\,s).
\item Start the observer; wait for \code{/api/ready} (120\,s).
\item Report \code{Running}.
\end{enumerate}

Each node runs with an environment reduced to \code{HOME}, \code{PATH},
\code{TMPDIR}, \code{LANG}, \code{OPENAI\_ENABLED=false}, \code{OLLAMA\_ENABLED=false},
and, for nodes with a key, \code{F1R3NODE\_VALIDATOR\_PASSWORD}. Stdout and stderr go
to the node's \code{.stdout.log}. Argument vectors:

\begin{lstlisting}
# bootstrap
f1r3node run --config-file "$STATE/conf/bootstrap.conf" \
  --bootstrap "rnode://$BOOT_ID@127.0.0.1?protocol=40400&discovery=40404" \
  --validator-private-key-path "$STATE/keys/bootstrap.pem" \
  --required-signatures $N0 --ceremony-master-mode --heartbeat-disabled \
  --host 127.0.0.1 --no-upnp --allow-private-addresses $TOKEN_FLAGS

# validator k (--genesis-validator only for k <= N0, and only until genesis is recorded)
f1r3node run --config-file "$STATE/conf/validator-$k.conf" \
  --bootstrap "rnode://$BOOT_ID@127.0.0.1?protocol=40400&discovery=40404" \
  --validator-private-key-path "$STATE/keys/validator-$k.pem" [--genesis-validator] \
  --host 127.0.0.1 --no-upnp --allow-private-addresses $TOKEN_FLAGS

# observer
f1r3node run --config-file "$STATE/conf/observer.conf" \
  --bootstrap "rnode://$BOOT_ID@127.0.0.1?protocol=40400&discovery=40404" \
  --heartbeat-disabled --host 127.0.0.1 --no-upnp --allow-private-addresses $TOKEN_FLAGS

TOKEN_FLAGS="--native-token-name F1R3CAP --native-token-symbol F1R3 --native-token-decimals 8"
\end{lstlisting}

\noindent
On the very first start the bootstrap's node id is not yet known; as in
\code{shard.yml}, it bootstraps from itself, and \Hr{} learns the id from its
\code{/api/status} before starting any other node.

\subsection{Health}
Every 10\,s the supervisor reads \code{GET /api/status} from every node. The shard is
\code{Degraded} when any node is not ready, when validators' last finalised blocks
differ by more than 20, when the observer trails validator~1 by more than 20 blocks for
more than 60\,s, or when no block has been finalised for 120\,s while
\code{/api/pending-deploys} at validator~1 is non-empty. The status machine is
\code{Stopped} $\to$ \code{Starting(stage)} $\to$ \code{Running}
$\rightleftarrows$ \code{Degraded(reason)}, plus \code{Resizing(step)} and
\code{Failed(reason)}.

\subsection{Restarts}
A node that exits unexpectedly is restarted with exponential back-off (1, 2, 4,
\ldots, 60\,s); the others keep running. Five unexpected exits of one node within five
minutes put the shard in \code{Failed}: the supervisor stops the whole shard, in the
order below, rather than leave a bonded validator down (Principle~5), and posts a
notification pointing at that node's log.

\subsection{Stop}\label{sec:shutdown}
On \code{SIGTERM}: \code{SIGTERM} to the observer and wait up to 30\,s; then to every
validator at once and wait up to 60\,s; then to the bootstrap and wait up to 30\,s;
\code{SIGKILL} whatever remains; exit 0. Validators stop together so that none is
bonded and absent while the others continue.

\subsection{Port conflicts at start}\label{sec:portfail}
If a recorded port is taken at start, the shard goes to \code{Failed} naming the port
and the holder (via \code{lsof}), and offers ``Choose new ports'' for the affected
node. Moving any node other than the bootstrap needs no other change; moving the
bootstrap rewrites every node's \code{--bootstrap}. No re-genesis is needed.

\subsection{Sleep and wake}
The nodes run under a launch agent, so App Nap does not apply. The supervisor holds a
\code{PreventUserIdleSystemSleep} assertion only during provisioning and resizes.

\section{Resizing the shard}\label{sec:resize}

A resize changes $N$ to $M$ with $2 \le M \le 10$. It is requested from the
configuration panel or with \code{ctl resize}. Two modes exist.

\subsection{In place (default)}

The running shard keeps its chain, registry, balances and \Gz{} configuration.
Validators are added at the lowest free slots and removed from the highest occupied
slots; validator~1 is never removed. The resize is a list of per-slot steps recorded in
\code{shard.toml} before the first is taken; each slot moves through the states below,
and a restart of \Hr{} resumes each slot where it stopped.

\paragraph{Growing: slot $k$ from \code{absent} to \code{active}.}
\begin{enumerate}[nosep]
\item \code{keyed}: allocate ports; generate the key, PEM and Keychain item; render
  \code{validator-$k$.conf}.
\item \code{funded}: sign, with the faucet key, a transfer to validator~$k$'s vault of
  the stake plus a fee reserve (1\,000 F1R3 + 1\,000 F1R3 by default), rendered with
  \code{gaze-wallet}'s transfer template; send it to validator~1; wait until the
  observer reports it finalised (\code{/api/deploy-finalization-status}) and the
  vault's balance (\code{/api/balance}) covers it.
\item \code{joining}: start the node (no \code{--genesis-validator}); wait for
  \code{/api/ready}, i.e.\ the last-finalised-state join has completed.
\item \code{bonding}: sign, with validator~$k$'s own key, the bond deploy
  (the bundled template \code{bond.rho}, which is the repository's example with
  the amount set to the stake); send it to validator~1, a bonded validator, never to the
  joiner (Finding~\ref{f:resize}); wait until it is finalised and its result is
  \code{(true, \_)}.
\item \code{active}: poll \code{GET /api/bond-status/\{pk\}} at the observer until
  \code{isBonded} is true, which happens at the next epoch boundary (at most
  \code{epoch-length} $= 10$ blocks).
\end{enumerate}
Slots grow one after another, so that every bond is submitted while the active set is
known; the panel shows each step.

\paragraph{Shrinking: slot $k$ from \code{active} to \code{absent}.}
\begin{enumerate}[nosep]
\item \code{retiring}: sign, with validator~$k$'s key, the withdraw deploy
  (\code{PoS!("withdraw", deployerId, ret)}); send it to validator~1; wait until
  finalised with result \code{(true, \_)}.
\item \code{left}: wait until the validator is no longer in the active set
  (\code{PoS!("getActiveValidators")} by exploratory deploy at the observer), at the
  next epoch boundary. Only now stop the node (Principle~5).
\item \code{paid}: wait for the payout after \code{quarantine-length} $= 10$ further
  blocks; sweep validator~$k$'s vault, less the fee, back to the faucet with a transfer
  signed by validator~$k$'s key.
\item \code{absent}: move the slot's data directory \code{nodes/validator-$k$/},
  its configuration and its PEM into a per-slot directory under
  \code{archive/<timestamp>/}; delete its Keychain item; free the slot.
\end{enumerate}
The node leaves consensus at step 2; steps 3 and 4 are bookkeeping and do not block a
further resize.

\paragraph{Failure.} If a step fails (a deploy rejected, a timeout of five epochs'
worth of blocks without the expected state), the resize stops at that slot, the shard
stays \code{Running} with the slots completed so far, and the panel offers ``Retry'' or
``Undo'', where undo runs the opposite procedure on the slots already changed. A slot
in \code{joining} whose bond never lands is stopped and archived, since it is not
bonded.

\subsection{As a new shard}

``Start a new shard with $M$ validators'' is the reset of \S\ref{sec:reset} with
$N_0 := M$: the current shard is archived and provisioning runs again from S1. It is
faster than growing by many slots and gives $M$ genesis validators with equal stakes;
it discards the chain. The panel says so.

\subsection{Invariants}
\begin{itemize}[nosep]
\item $2 \le N \le 10$ at every step; a request outside the range is refused by the
  supervisor as well as the panel.
\item Validator~1 is always active; \Gz{}'s \code{validator} setting never changes
  during a resize.
\item At most one resize is in progress; start, stop and reset are refused while one
  runs, except ``Stop'', which first finishes or undoes the current step.
\end{itemize}

Threat & Protection\\
\midrule
Reuse of public development keys & All keys generated at S3 or at resize; the release pipeline greps every artifact for the public keys in \code{docker/.env.example} and fails on a match.\\
Another user on the Mac & State directory \code{0700}, PEMs \code{0600}; no key in any argument vector; each PEM password only in the Keychain and in its own node's environment; faucet key never given to a node; control socket checks the peer uid.\\

\section{Upgrade, reset and uninstall}\label{sec:lifecycle}

\subsection{Upgrade}\label{sec:upgrade}
A newer archive replaces both bundles. The supervisor, restarted by launchd, compares
the new \code{f1r3node}'s storage format (N4) with the one recorded at genesis. If
compatible, it restarts every node on its data, finishing any interrupted resize. If
not, it does not start; the panel offers ``Start a new shard'' with the current $N$,
which archives the shard and re-provisions from S3, funding the wallet again. A resize
in progress blocks an upgrade's restart until the current step completes.

\subsection{Reset}\label{sec:reset}
``Reset shard\ldots'' stops the shard, moves \code{nodes/}, \code{genesis/},
\code{conf/} and \code{keys/} into a timestamped directory under \code{archive/}, deletes the Keychain
items, and re-runs provisioning from S1 with the chosen $N_0$ (the current $N$ by
default). The dialog says that every deploy, registry entry and balance on the local
shard will be gone, and that \Gz{} wallets are untouched and the active one will be
funded again.

\subsection{Uninstall}\label{sec:uninstall}
Stop the shard; unregister the agent; after a second confirmation remove the state
directory (optionally keeping \code{archive/}), the logs and every Keychain item of
service \code{io.f1r3fly.ign1t10n}; remove \Gz{}'s managed block or drop-in; move
\code{ign1t10n.app} to the Trash; \code{pkgutil --forget io.f1r3fly.ign1t10n.pkg}.
\Gz{}, its profile and its wallets are left alone.

\section{Testing and acceptance}\label{sec:accept}

\begin{description}[leftmargin=1.5em,style=nextline,itemsep=2pt]
\item[A1 Clean install.] On a fresh user account, the archive (plus one background-item
  approval) ends with \Gz{} open and \code{ctl status} reporting \code{Running, 2
  validators}, within five minutes.
\item[A2 Round trip through the browser.] \code{f1r3gaze --headless} on a test page
  that inserts into the registry is signed by the funded wallet, sent to validator~1,
  reported finalised, and read back at the observer.
\item[A3 Loopback only.] \code{lsof -nP -iTCP -sTCP:LISTEN} lists no \code{f1r3node}
  socket on an address other than \code{127.0.0.1}.
\item[A4 No foreign libraries.] \code{otool -L} on every Mach-O lists only system paths.
\item[A5 No shipped secrets.] No public key in \code{shard.toml} appears in
  \code{docker/.env.example}; PEMs are \code{0600}; \code{ps -Eww} by another user
  reveals no key or password.
\item[A6 Persistence.] After a reboot, the shard returns to \code{Running} with the
  same genesis hash, the same $N$, and a height no lower than before.
\item[A7 Port conflict.] With \code{docker/shard.yml} running (which occupies the
  default plan), provisioning allocates other bases and A2 passes.
\item[A8 Crash recovery.] \code{kill -9} of any one node leads back to \code{Running};
  six rapid kills of one validator stop the whole shard in \code{Failed}.
\item[A9 Upgrade.] $v$ to $v{+}1$ keeps the chain and $N$ with a compatible storage
  format; with an incompatible one the shard is archived only after consent.
\item[A10 Uninstall.] No state, logs, Keychain items or agent remain; \Gz{} and its
  wallets are untouched.
\item[A11 Grow in place.] From $N=2$, \code{ctl resize 5}: validators 3--5 reach
  \code{active}, \code{/api/bond-status} is true for each, and a deploy sent during the
  resize and one after it both finalise. The chain's height never decreases.
\item[A12 Shrink in place.] From $N=5$, \code{ctl resize 3}: validators 5 and 4
  withdraw, leave the active set before their processes stop, are paid out, and are
  swept to the faucet; deploys finalise throughout; validator~1 is untouched.
\item[A13 New shard at the maximum.] ``Start a new shard with 10 validators'' produces
  a genesis with ten bonds and A2 passes.
\item[A14 Bounds and interruption.] \code{ctl resize 1} and \code{ctl resize 11} are
  refused; killing the supervisor during each growing and shrinking step and restarting
  it completes the resize.
\end{description}

The matrix is macOS 13, 14, 15, 26 and the current release on Apple silicon, and 13
and 15 on Intel while x86\_64 is shipped; A11--A13 also run on the smallest supported
memory configuration to calibrate the panel's warnings.

\section{Obligations and decisions}\label{sec:open}

\begin{obligation}[The loopback shard works]\label{ob:topology}
Before H2 is merged, N3 must show the \code{shard.yml} topology running with every node
on \code{127.0.0.1} and distinct ports, for $N = 2$ and $N = 10$.
\end{obligation}

\begin{obligation}[Resizing works]\label{ob:resize}
Before H4 is merged, N3 must show one validator joining, bonding and becoming active,
and one withdrawing, leaving and being paid out, with the shard configuration's epoch
and quarantine lengths, and with deploys finalising throughout.
\end{obligation}

\begin{obligation}[Footprint]\label{ob:footprint}
T1 measures, at the pinned node version, each role's resident memory and disk after one
hour of a light deploy load, for $N = 2$ and $N = 10$; the figures are compiled into
\Hr{} as $M_{\min}$, $D_{\min}$ and the panel's estimates, and re-measured whenever the
pinned node changes.
\end{obligation}

\begin{obligation}[Measured fault tolerance]\label{ob:tolerance}
For each $N$ from 2 to 10, T1 measures how many validators may be stopped while blocks
continue to finalise, under \code{fault-tolerance-threshold = 0.1}, and the panel shows
that table. With $N = 2$ the expectation is none; the panel says so plainly.
\end{obligation}

\begin{obligation}[PEM compatibility]\label{ob:pem}
The PBES2 parameters of \S\ref{sec:ign} must be accepted by the OpenSSL that N2
vendors; the round-trip test in H1 proves it in CI.
\end{obligation}

\begin{decision}[Fold the bootstrap into validator~1]\label{dec:bootstrap}
The bootstrap costs one node's memory and adds a process that proposes nothing. A
bonded ceremony master exists already (standalone mode is one), so validator~1 could
take the role, leaving exactly $N$ validators plus the observer. Proposed: keep the
tested \code{shard.yml} shape for version 1 and revisit once N3 is green.
\end{decision}

\begin{decision}[Intel]\label{dec:arch}
Universal binaries, as \Gz{} ships, or Apple silicon only, which also matters more now
that ten validators is a supported configuration.
\end{decision}

\begin{decision}[Minimum macOS]\label{dec:macos}
13.0, for \code{SMAppService}.
\end{decision}

\begin{decision}[Genesis amounts and stakes]\label{dec:amounts}
One million F1R3 to the browser's wallet, 1\,000 F1R3 of fees and a stake of 1\,000 to
each validator, the rest to the faucet; or stakes chosen per validator in the panel.
\end{decision}

\begin{decision}[Where deploys go]\label{dec:deploytarget}
Always validator~1 (proposed), or \Gz{} rotating across validators with G4.
\end{decision}

\begin{decision}[Heartbeat and loop timing]\label{dec:heartbeat}
Keep \code{default.conf}'s timings (casper loop 750\,ms, heartbeat on) or tune them for
a laptop once T1 has measured finalisation latency and idle CPU at $N = 10$.
\end{decision}

\begin{decision}[Cross-origin requests]\label{dec:cors}
Whether the node should refuse HTTP requests carrying a foreign \code{Origin} header,
so that pages in other browsers cannot use the local shard's API.
\end{decision}

\begin{decision}[Embers]
Whether a later version bundles Embers, so that transfers, not just balances, work in
\Gz{} against the local shard.
\end{decision}
